## Admission and normal exit

The future launcher must run from the single fixed cooperative generation root
in `Get-Business5244CooperativeExitCase`. Its owner and controller entry files,
13-file critical source closure and manifest are sealed by retained native file
handles. The manifest's exact SHA256 is part of both processes' command lines.
The plan alone is not authority: the owner also needs its genuine Owner lease,
native child creation handle, original process/thread/runspace and a retained
query-only handle to the one expected controller PID/native birth/SID/exe/argv.
No new ACL, credential, network endpoint or terminate permission is introduced.

Only this opt-in owner accepts `exit` on the existing local authenticated pipe.
Default Cold, steady and supersession owners keep their status-only guards.
The original 15-second input nonce and separate monotonic 60-second admission
remain unchanged. Retire/recover are rejected by the opt-in normal-exit owner.

Before leaving supervision, it consumes the once state, durably writes a new
intent and creates the existing canonical pending barrier with CreateNew. It
then revalidates the same admission, native identities, sources and Owner lease.
Malformed, stale, wrong-controller or unconfirmed writes never cause the loop
to exit. An uncertain attempt is not retried. Partial evidence is preserved.

Accepted exit breaks the owner's own supervision loop. The existing finally
closes the pipe, native child/Job and pinned children, then releases the real
lease/witness. A private context records the successful RETURN of lease release;
its prematurely set `closed` flag is not sufficient. The genuine context returns
to the future outer launcher only after normal cleanup succeeds. That launcher
must finish Cold disposal before calling `Complete-Business5244CooperativeExitCleanup`.
The native Cold completion property is set only at the end of disposal.
Source seals are released before the final durable receipt; journal directory
identities stay pinned and revalidated until the write and handle cleanup finish.

## Outcome and failure boundary

ACK delivery is not completion. The exit exchange may lose its reply as the
owner normally closes the channel. Do not resend exit. The controller must
reconcile the original generation/intent/receipt, retained native owner exit
and normal acquisition of the SAME preheld non-abandoned startup mutex. A JSON
receipt alone never authorizes installation, restart, archive or rollback.

The pending barrier and all once/intent/receipt evidence remain in place.
Normal startup is therefore blocked after exit. This component does not clear,
archive or supersede the barrier and does not install a successor. Failures
before accepted exit preserve the running child; failures after acceptance or
during cleanup remain UNKNOWN without a clean receipt/native-exit proof. They
require a separately supported recovery path, not automatic restore or replay.
