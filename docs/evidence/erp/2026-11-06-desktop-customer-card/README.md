# R1 K04-05: customer list, selected card and account hierarchy

The existing acceptance requires search/paging/back navigation to retain the correct customer and account, and late replies not to select a different card. The green list now offers code/name/phone/city/country search, customer card opening, and session-scoped list page/search restoration. Card close keeps the same list; opening the card's last completed invoice and returning through navigation restores that list. Logout/login clears navigation memory.

The readonly rich-profile service checks the same target/role guards and current normal session under one SERIALIZABLE transaction. Every currency account must belong to the selected customer and party, have no supplier parent, unique identity/currency and a known local balance. The exact primary-currency legacy balance must match its account. TRY/USD/EUR balances stay separate, without an invented combined total or currency account creation. A malformed/foreign/missing balance fails closed. `customer.view` reads the card; `sales.view` additionally allows the last finalized/COMPLETED desktop sale. Both permissions are checked in one lease; the browser cannot request the history permission through a query parameter. No cost/profit is exposed.

The shared card contract, route and normal browser core bind selected identity and account parents. Disposed or late logout responses cannot replace another customer's card. The last-sale action uses only the validated stored invoice. Readonly source review found a P2: opening a card could discard an unsent customer form. The fix adds dirty/busy/pending close protection, an explicit keep/discard flow, and locked fields while a request is in flight. COMMITTED results can still refresh the list. The reviewer rechecked the fix and reported no remaining concrete P1/P2 without running SQL/UI/tests.

Seventy affected source test files and the guarded 26-module green build passed. Coverage includes real normal auth/HTTP assembly with a synthetic SQL driver, route history-permission separation, account-parent and balance failures/rollback, exact multiple-currency presentation, late/foreign responses, escaped phone/country paging and dirty/pending form retention. The first wider run exposed a paging-test fixture with a stale total; its count and SQL-query selection were corrected without changing production guards. Original failed and successful logs are retained. A misdirected local editing command was reversed from the last committed frontend file and the narrow intended diff reapplied; the running application was never changed by that failed edit.
