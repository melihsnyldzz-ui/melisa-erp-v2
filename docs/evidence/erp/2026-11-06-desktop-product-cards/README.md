# R1 product cards and additional barcodes

Scope: K03-02 leading-zero primary/additional barcodes and K03-01 complete readonly product-card reopening in the existing dedicated desktop schema 3. PR54 remains the base product workflow. No new table, migration, grant, SQL service operation, sale or restore is required.

Rich product creation accepts up to ten additional barcode strings. All active barcodes are checked under the native Turkish_CI_AS SQL collation and SERIALIZABLE transaction before product writes; input-equivalent codes receive a durable rejection in the existing UUID/actor/body journal. All inserted barcode IDs, product parents, codes and primary flags are read back in the same transaction. Old pending bodies without the optional array keep their original shape. An unknown response retains the original UUID/body; a confirmed durable rejection preserves the editable draft.

Product search prioritizes an exact active barcode and relates every barcode to its product. The full card is a readonly transaction with current session, product.view and product.edit checks; purchase/cost fields are not exposed to a view-only user. Both API and normal frontend facade validate the selected product and all barcode parents. The responsive product form/card stylesheet is included in the hashed package manifest and served through the existing fixed loopback asset allowlist.

Source validation: 64 focused test files passed under the offline guard, including real HTTP application/auth/store assembly with a synthetic driver, retry/rejection persistence, wrong-parent and permission rejection, exact barcode predicate, card render disposal, and hashed CSS serving. The guarded green-screen build passed. Independent readonly source review found no concrete P1/P2. These results do not establish real SQL locking, installed GUI, physical scanner or human acceptance. Installed evidence will be recorded separately after the controlled R1 package transition.
