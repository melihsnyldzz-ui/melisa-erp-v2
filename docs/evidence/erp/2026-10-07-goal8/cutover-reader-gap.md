# Goal8 additive FINAL publication — source contract and remaining proof

This is source-only technical preparation. No SQL was executed, no real T1 was captured, no runtime was restarted, and no human or LIVE acceptance is recorded here.

## Concrete consumer and transaction contract

`scripts/migration/final-cutover-price-reader.mjs` exports `createFinalPricePublication({baseline,expectedBaselineHash,baselineContext,evidenceKind})`. The supplied baseline is the complete immutable current Goal7 resolved product/typed-price snapshot and its referenced stage records, sealed and bound by its separately approved hash. Historical product lineage and classification payloads remain unchanged, including the accepted 49 new and 12 master changes; only changed typed price atoms receive new FINAL stage lineage. Inverse publishes another fresh `FINAL-INVERSE-<cutover UUID>` snapshot restoring original typed price lineage with the current inverse native witness.

The driver receives `{contractHash,publish,verify}`. `contractHash` binds the implementation functions and baseline/configuration. The already approved cutover transaction supplies `query`, `plan`, `receipt` and `inverse`; importing this module cannot connect, capture, or execute SQL. Publication is anchored to original planHash, childId and effectsHash, avoiding circular receipt hashing. The returned durable object contains publicationHash, snapshotHash and versionContext. `partyBindingsHash` is the hash of the original plan's account rows for the independently sealed party reader.

The publisher inserts only fresh version rows and four new run-specific procedures into the existing immutable Goal7 version tables. Existing procedures, bindings and defaults remain untouched. It grants execution only to the existing two TEST principals, failing if absent. Before commit it checks actual OBJECT_DEFINITION hashes, executes the normal catalog/stock reader for every price product, requires unheld cards and exact sales tuples with actual actor permission, and executes normal opening detail/list readers. Missing publication, native drift, incorrect full counts, reader failure or a failed permission check aborts the transaction.

API catalog/stock/opening readers opt into an explicitly verified `melisa-final-catalog-context.v1` context and its four exact procedure names/hashes. API DTOs, the immutable classification registry and the existing green catalog envelope accept only pinned ancestral runs/dates under that context. No configured FINAL context keeps the accepted old default. A rejected requested context cannot fall back. `freshLive` remains false; synthetic evidence never becomes real source T1.

## Native SQL proof and bounded fixture

Offline tests exercise immutable snapshots, fresh forward/inverse lineage, exact decimal witnesses, drift rejection, full deterministic synthetic 16671-product/63775-price reader generation, and old/default reader regressions. Generated SQL is not SQL Server execution proof. No actual normal-reader publication or inverse SQL acceptance is claimed.

The small isolated cutover fixture has one anonymous product and cannot satisfy the genuine normal readers' complete accepted scope and historical readiness. Substituting counts, bypassing guard hashes, or a Boolean verification hook would not close this item.

A credible native fixture must provide the complete historical contract: accepted RUN06 manifests/products/prices/stage records; complete current Goal7 immutable manifest/products/prices/records; native products, units, typed prices, aliases, stock/provenance; 54 held cards and quarantine bindings; role/permission data; complete classification/media metadata; and every readiness procedure/trigger definition used by the actual SQL readers. Exact object definitions and full counts are part of the contract. The existing mini-schema rewriting helper changes object definitions, so its installed hash pins need an independently derived fixture contract rather than assumed production pins.

The bounded source entry point `runGoal8FinalReaderFixture` in `scripts/canonical/goal8-final-reader-fixture.mjs` accepts an injected SERIALIZABLE driver, exact metadata export and explicit TEST fixture authorization. It creates only two new fixture namespaces and metadata-only tables; all seeded rows are deterministic synthetic values. Native SQL FOR JSON hashes must be read before sealing the full 16671-product/63775-price baseline. Four generated FINAL readers retain their changed manifest/count/ancestry/native/stage/alias/NULL/type/DTO/actor checks and actual immutable version guards. Only the exact unchanged historical readiness blocks are omitted from this instrumented fixture, with their original hashes recorded; `historicalReadinessReproved:false` makes that accepted-baseline dependency explicit. Production builders and readers receive no fixture instrumentation.

The driver entry point performs typed native price changes including zero-to-one, appends a fresh immutable FINAL snapshot, checks installed definitions and all four actual SQL reader outputs, executes rollback-only seal/native/permission/tuple rejection cases, and publishes a fresh inverse snapshot restoring zero/prior prices and lineage while an unbound native NULL slot stays NULL and absent from all sealed typed rows. Offline tests pass; this document does not claim that the injected SQL runner has executed. Its result must remain `SYNTHETIC_NATIVE_SQL`, `actualT1:false` and `normalErpRuntimeActivated:false`.

Actual API process activation remains a separate concrete configuration step: the admin publisher's durable `versionContext` does not automatically configure an already running API. A browser must render those endpoint results. Existing shared CRM readers must validate the FINAL contract or reject the unknown version; old-context fallback is not acceptance of FINAL.

Until that native API/browser/shared-CRM chain is proved, final cutover remains NOT READY. Physical Zebra/reboot acceptance and real source freeze/T1/configuration/permission acceptance remain separate pending steps. This source adapter does not create business approval or remove D01/D02 holds.
