# R1 K01-06: visible version, target and safe errors

The home screen offers an explicit installation-information view: dedicated local TEST target, manifest package SHA-256, creation time in UTC, schema version and local-only access. It clearly identifies the installation as a test candidate. The worker derives the metadata from the manifest bytes it has already hashed and validated; the owning parent keeps the manifest and all imported sources pinned and read-locked throughout its lifetime. The shared public model admits only nine scalar fields and fixed TEST identity. Credentials, connection strings, paths, arbitrary metadata and foreign targets are rejected, not rendered.

The endpoint is GET-only and requires the current normal session, fixed loopback/origin and no query parameters. It adds no permissions, users or SQL operations. Older v2 factories do not receive this v3 metadata route. The browser core checks current session generation and the full public contract; the disposed lazy view ignores late replies. Read failures show a finite useful retry message without raw exception text; the list error also gives a plain session/connection recovery instruction.

Seventy-two affected source test files and the guarded 28-module green build passed. Tests cover actual normal auth/HTTP assembly with a synthetic SQL driver, missing auth/query rejection, fixed target, exact public fields, invalid timestamps, getters/extra secret fields, late logout/dispose replies and safe failure rendering. The first wider run required registering the new static `DESKTOP_RUNTIME_INFO_INVALID` code in the existing closed logger vocabulary; only that reviewed literal was added, arbitrary error text remains redacted. Original failed and successful logs are preserved. Independent readonly review found no concrete P1/P2, including worker pin/import lineage; it ran no SQL/UI/tests.

Installed verification is pending: compare displayed/API values to the actual manifest and SQL target, exercise a readonly connection-failure message only if supported by the browser tool, restore normal access and verify recovery. Independent before/after SQL must remain identical. A readonly network failure is not lost-ACK or double-write acceptance. No DDL, permission, SQL service, account or business-data change is required; human/device/LAN/LIVE and remaining ERP functions stay open.
