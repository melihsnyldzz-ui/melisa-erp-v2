# R1 product conflict — source correction and preceding SQL rollback proof

A duplicate stock code/barcode previously reached the unique constraint after earlier product inserts and left the request conservatively UNKNOWN. The pending screen could only retry that same failing request. The new rich-product path checks both native unique predicates under SERIALIZABLE/UPDLOCK/HOLDLOCK, after the existing normal-session authority, active supplier and UUID application-lock checks, before business inserts. If a conflict exists it stores an exact rejection in the existing request journal, with the original operation/actor/body hash, and reads it back before commit. No DDL, new account, grant or SQL service change is needed.

Only a committed, validated durable rejection returns409/NOT_COMMITTED. A lost acknowledgement remains UNKNOWN until the same body/UUID is recovered; a recorded rejection replays409 without a second journal or product effect. A prior committed product still replays COMMITTED. Changed body/actor, invalid authority, malformed input or unverifiable result stays UNKNOWN. New stock codes and barcodes still rely on the native unique constraints as well as the locked check.

The browser accepts only the exact authenticated409 contract. The pending request is atomically replaced in the same local-storage key by a version2 rejected draft containing its actor, original body and rejection. Reopening the screen restores all fields, including supplier selection. Input fields are disabled during submission. Unknown requests retain the original version1 body/UUID. The original V2 profile and legacy pending replay remain supported.
