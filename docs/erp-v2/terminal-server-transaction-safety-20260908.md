# Terminal sale transaction safety — 2026-09-08

A terminal event now owns one SQL transaction covering the exact event lock, durable ledger, customer/product checks, invoice draft, finalization, audit and result snapshot. Retrying the same event with the same actor and payload returns the stored finalized result. A different actor, changed payload, invalid ledger or unverifiable legacy invoice fails closed. The ledger schema must include the existing non-null unique client key; the handler never creates schema.

Draft creation and sales finalization accept an internal transaction context while retaining their existing standalone behavior. Cash-customer preparation participates in that context and runs once. Product locks use ascending IDs. Collections and supplier payments acquire party locks before finance-account locks. Finance reads now check schema using SELECT rather than creating tables or inserting default accounts. Missing finance schema returns FINANCE_ACCOUNT_SCHEMA_MISSING, referencing the existing 0012 migration.

The installed mssql 12.5.4 native transaction implementation calls callback(null) even when COMMIT/ROLLBACK SQL fails. A wrapper propagates those failures, marks the affected connection unhealthy and avoids reporting a successful transaction event. Uncertain commit or rollback produces TERMINAL_SALE_OUTCOME_UNVERIFIED and requires manual review. This is integrated with the client queue's existing manual-review handling.

The reviewed f639 worktree supplied the core implementation. Its unrelated switch from Vega product reads to local products was excluded. The candidate's exact Vega product search/barcode functions and Vega sale prohibition remain. The submit entry point additionally invokes the existing Melisa write guard before SQL preparation. No messaging handler, route or test is included.

Validation at this milestone: 96 network/process-denied API tests pass, including seven tests executing the actual submit handler with transaction-bound SQL/invoice doubles. They cover same-event replay, simultaneous duplicate submissions, changed payload/owner rejection, failures at every post-reservation step, a lost commit response, missing schema/legacy records and Vega/read-only rejection before SQL. Other tests cover native driver boundaries, ledger validation, shared finalization preparation and lock ordering. All four applications pass checkJs (149/182/34/3 source roots, zero diagnostics); lint, web build and terminal regression tests pass.

These tests prove code behavior and transaction binding, not real SQL locking or rollback.
