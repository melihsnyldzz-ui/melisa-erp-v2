## Purpose

This document is the current business and delivery status baseline for Melisa ERP v2.

It exists because the implementation has moved faster than the older documentation. Before more code work continues, humans and AI agents need one clear view of what is ready, what is partial, what is risky, and what is local-only.

## Executive Summary

Melisa ERP v2 is no longer a skeleton project. It is an active multi-app ERP repository with:

- Express API connected to SQL Server.
- React/Vite web-admin.
- Expo terminal app.
- Electron desktop shell.
- SQL Server migrations.
- ERP documentation and AI agent entrypoint.

The next business priority is not new modules. The next priority is making ERP Core reliable:

1. Authentication and permissions.
2. Product and stock data.
3. Customer and supplier ledgers.
4. Sales and purchase commercial truth.
5. Finance collections and payments.

Growth, CRM, media automation, Mission Control, and AI should wait until ERP Core is stable.

## Known Risk Areas

| Risk | Severity | Current position |
|---|---|---|
| Live SQL Server writes | Critical | Must require explicit human approval before tests, migrations, reset, cleanup or production writes |
| `.env.local` and secrets | Critical | Must never be exposed or committed |
| WhatsApp/external sending | Critical | Must not send real messages without explicit human approval |
| Backup/reset scripts | Critical | Sprint 007 documented the runbook and locked backup execution behind explicit `--execute` and confirmation; reset/restore still require explicit Melih approval and verified target DB |
| Local uploads and product images | High | Not fully represented in Git; image links may depend on local DB/files |
| Existing imported business data | High | May contain duplicates, incomplete fields or inconsistent source data |
| Mock/demo boundaries | High | Must be isolated so operators do not see mock data as live truth |
| Permission gaps | High | Supplier/finance/import permissions need controlled review |
| Visual layout at different resolutions | Medium | Known class of issues; requires visual QA sprint |
| README drift | Medium | Root README still contains older skeleton-era language |

## Local-Only Data Boundaries

GitHub source code does not represent the full running ERP state.

The following are local/runtime concerns:

- SQL Server database content.
- Uploaded product images.
- Backup files.
- `.env.local` credentials and secrets.
- Local logs.
- Local terminal/Electron runtime state.
- Tool-specific folders such as `.claude/`.

Any AI or human reviewer must understand that GitHub can show application code and documentation, but not the complete live product/customer/supplier/image state.

## Current Sprint Baseline

Sprint 009 is completed when operators have a read-only Operational Health screen for API/SQL status, terminal pending/failed sync counts, import/finalize visibility notes, recent audit events, and anomaly watch points; the route remains protected by `audit.view`; and no DB write, migration, reset, restore, cleanup, WhatsApp send or production deploy was run without approval.

Sprint 009 does not create automatic alerting or repair actions. It creates a visible operator surface and documents the remaining gap that import/finalize failures are not yet persisted as dedicated failure-job metrics.
